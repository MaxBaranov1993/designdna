# DesignAI Web — план создания SaaS для генерации UI/UX-дизайна

> Конкурент Claude Design / v0, но с **ручным управлением**: генерация не картинками, а редактируемыми UI-структурами, управление через ноды (как ComfyUI), правка результата как в Figma, цикл «сгенерировал → поправил руками → подал обратно как промпт».

---

## 1. Продуктовая идея

**Что делаем:** SaaS, который генерирует веб-дизайн (компоненты, секции, целые страницы) как **реальную, редактируемую UI-структуру** — дерево компонентов + дизайн-токены (цвета, типографика, отступы, радиусы, тени). Никаких картинок: результат — живой HTML/React-компонент, который можно двигать, менять и дорабатывать.

**Отличие от v0 / Claude Design / Figma Make:**
- Генерация управляется **нодовым графом** (аналог ComfyUI): промпт-ноды, модель-ноды, стайл-ноды, микс-ноды с весами, вариант-ноды.
- Результат редактируется на канвасе как в Figma, и **отредактированная версия сериализуется обратно в промпт** для следующей итерации.
- Консистентность через жёсткий слой дизайн-системы (токены + библиотека блоков), а не «надежда на модель».

**Ключевой цикл пользователя:**
```
Промпт-нод → Генерация (Kimi/Qwen) → Варианты на канвасе
   → Микс вариантов с весами → Ручная правка (Figma-like)
   → «Продолжить от этой версии» → новая итерация → Готовая страница из блоков
```

## 2. Модели (что есть и как использовать)

### Kimi (Moonshot AI)
| Модель | Роль в продукте |
|---|---|
| **Kimi K2.5 / K2.6** | Основной «дизайнер». Нативная мультимодальность (скриншоты/мокапы на вход), сильная генерация фронтенда: интерактивный UI, динамические лейауты, анимации. Контекст 256K — влезает вся дизайн-система + RAG-контекст. |
| Kimi K2 Thinking | Тяжёлые задачи: архитектура страницы, план дизайн-системы, декомпозиция сложного брифа. |

API: `https://api.moonshot.ai/v1` (OpenAI-совместимый), цены ~$0.6/1M input, $3/1M output.

### Qwen (Alibaba Cloud, DashScope)
| Модель | Роль в продукте |
|---|---|
| **qwen3-coder-plus** | Генерация/рефактор кода компонентов, строгий структурированный вывод (JSON mode) — идеален для выдачи дерева компонентов по схеме. |
| **qwen3-max** | Промпт-инжиниринг клиента: дотюнивание сырого запроса пользователя в детальный дизайн-бриф (с опорой на нашу базу знаний). |
| qwen-vl-max | Анализ референсов: скриншот → описание (стиль, палитра, сетка, типографика) для базы знаний и для ноды «референс». |

API: DashScope OpenAI-совместимый endpoint:
`https://dashscope-intl.aliyuncs.com/compatible-mode/v1`

### GLM (Zhipu AI)
| Модель | Роль в продукте |
|---|---|
| **glm-4v** | Vision-анализ структуры UI для pixel-perfect reproduction: скриншот → иерархия компонентов, типы блоков, layout. НЕ для извлечения точных цветов/размеров (это делает Python из пикселей). |

API: `https://open.bigmodel.cn/api/paas/v4` (OpenAI-совместимый).

### Распределение ролей (важно для качества и цены)
1. **qwen3-max** — усиление промпта пользователя (RAG из базы знаний).
2. **Kimi K2.5** — генерация дизайна (дерево компонентов + токены), несколько вариантов.
3. **qwen3-coder-plus** — нормализация вывода в нашу JSON-схему, починка невалидного результата, экспорт в код.
4. **Kimi K2.5 (vision)** — критик-проход: рендер результата → скриншот → «что не так с дизайном» → автофикс. Это даёт консистентность и «красивость».
5. **GLM glm-4v (vision)** — pixel-perfect reproduction: анализ структуры скриншота (компоненты, layout, иерархия). Точные значения (цвета, bbox, radius) извлекаются Python-скриптами из пикселей, не из VLM.

## 3. Ядро: представление дизайна (самое важное решение)

Генерируем **не код и не картинку**, а промежуточное представление — **Design IR** (JSON):

```json
{
  "tokens": {
    "color": { "primary": "#5B5BD6", "bg": "#0E0E12", "text": "#F5F5F7" },
    "font": { "display": "Sora/600", "body": "Inter/400" },
    "radius": { "card": "16px" },
    "spacing": { "section": "96px" }
  },
  "tree": {
    "type": "Section", "variant": "hero-split", "props": {...},
    "children": [
      { "type": "Heading", "text": "...", "size": "display-xl" },
      { "type": "Button", "variant": "primary", "text": "..." }
    ]
  }
}
```

- Компоненты — из **нашей библиотеки блоков** (закрытый набор: hero, features, pricing, navbar, footer, card, form, testimonial, gallery…). Модель *собирает и стилизует*, а не пишет с нуля → консистентность гарантирована архитектурно.
- Design IR рендерится в React/Tailwind (preview), экспортируется в HTML/React/Tailwind/Figma (позже — через plugin API).
- Ручная правка на канвасе меняет тот же IR → при «продолжить от этой версии» IR + diff сериализуются в промпт.

## 4. Нодовая система (аналог ComfyUI)

Canvas с графом на **React Flow**. Типы нод:

| Нода | Вход → Выход | Описание |
|---|---|---|
| **Prompt** | текст → текст | Сырой запрос пользователя |
| **Prompt Enhancer** | текст → бриф | qwen3-max + RAG из базы знаний: превращает «сделай лендинг для кофейни» в детальный бриф со стилем, палитрой, референсами |
| **Style / Theme** | — → токены | Набор токенов (вручную, из пресета, из референса) |
| **Reference** | скриншот/URL → стиль | qwen-vl разбирает референс в токены + описание |
| **Reproduce** | скриншот → HTML + diff | GLM glm-4v (структура) + Python-измерения (цвета, bbox, radius из пикселей) + PNG-иконки base64 + absolute positioning + Playwright screenshot + pixel diff по регионам; цель: diff < 5% |
| **Generator** | бриф + стиль → N вариантов IR | Kimi K2.5, параметры: модель, температура, количество вариантов, seed |
| **Mix** | 2–4 IR + веса → IR | Взвешенное смешение: токены интерполируются (цвета в OKLCH, размеры численно), структура берётся от доминиантного веса или собирается моделью по «взвешенному» мета-промпту |
| **Variant / Batch** | 1 → N | Параллельные варианты с разными температурами/стилями |
| **Critic** | IR → IR + отчёт | Рендер → скриншот → Kimi vision: контраст, сетка, иерархия → автофикс |
| **Edit (Canvas)** | IR → IR | Ручная правка как в Figma; diff сохраняется |
| **Compose Page** | N блоков → страница | Сборка целой страницы из понравившихся блоков |
| **Export** | IR → код | HTML / React+Tailwind / (позже Figma) |

Веса микса — слайдеры на ноде, как у LoRA-весов в ComfyUI. Граф сохраняется как JSON (проект = граф + все IR-версии).

## 5. Figma-like редактор

- Канвас: **React + собственный рендер** поверх Design IR (выбор элемента, рамки, guides), либо старт на tldraw/Konva — но кастомный рендер IR проще, т.к. элементы — реальные DOM-компоненты.
- Правки: перемещение/ресайз (меняет layout-пропсы), текст, цвета/шрифты/отступы через инспектор (меняет токены), замена варианта блока, удаление/дублирование секций.
- Всё — операции над IR с undo/redo (command pattern).
- «Подать как промпт»: `diff(beforeIR, afterIR)` → «пользователь увеличил отступы, сменил палитру на тёплую, заменил hero на centered» → контекст следующей генерации.

## 6. База знаний веб-дизайна (RAG для дотюнинга промптов)

**Источники (метаданные и публичные описания, не контент):**
- Awwwards, SiteInspire, Land-book, Lapa Ninja, Mobbin (паттерны), Godly — каталоги лучших сайтов: теги, стили, отрасли, паттерны.
- UI-киты и библиотеки: Tailwind UI, shadcn/ui, Chakra, Untitled UI — структура компонентов и naming.
- Дизайн-системы: Material, Apple HIG, Polaris, Carbon — правила типографики/сеток/контраста (WCAG).

**Хранилище:** PostgreSQL + pgvector (один сервис вместо двух). Запись: `{описание, стиль-теги, отрасль, палитра, типографика, паттерны, эмбеддинг}`.

**Использование:**
- Prompt Enhancer ищет топ-K похожих примеров по запросу пользователя и подкладывает в бриф («в этой нише работают: тёмная тема, крупная серифная типографика, ассиметричная сетка»).
- Авто-тегирование стиля результата → пользователь фильтрует варианты («покажи более minimal/swiss»).

⚠️ Юридически: собираем описания, теги и собственный анализ скриншотов, а не перепечатываем чужой код/дизайн 1-в-1.

## 7. Архитектура системы

```
┌─────────────────────────────────────────────────┐
│ Frontend (Next.js + React)                       │
│  ├─ Node graph editor (React Flow)               │
│  ├─ Canvas editor (кастомный рендер Design IR)   │
│  ├─ Preview (live React/Tailwind + скриншотер)   │
│  └─ Библиотека блоков / инспектор токенов        │
├─────────────────────────────────────────────────┤
│ Backend API (Node/Nest или Python/FastAPI)       │
│  ├─ Orchestrator генерации (очередь, BullMQ)     │
│  ├─ LLM Gateway: Moonshot + DashScope (ретраи,   │
│  │   валидация JSON-схемы, fallback)             │
│  ├─ Prompt Enhancer + RAG (pgvector)             │
│  ├─ Critic service (рендер → скриншот → vision)  │
│  └─ Export service (IR → HTML/React)             │
├─────────────────────────────────────────────────┤
│ PostgreSQL + pgvector │ Redis (очереди, кэш)     │
│ S3-совместимое хранилище (скриншоты, превью)     │
└─────────────────────────────────────────────────┘
```

- Валидация IR: JSON Schema + zod; невалидный вывод → qwen3-coder-plus чинит (repair loop, до 2 попыток).
- Стриминг вариантов на фронт по WebSocket/SSE, каждая нода-генератор — задача в очереди.
- Рендер для критика: headless Chromium (Playwright) → скриншот.

## 8. Дорожная карта

**Фаза 0 — Spike (1–2 нед)**
- Определить JSON-схему Design IR (30–40 типов блоков).
- Проверить: Kimi K2.5 генерирует валидный IR по схеме; qwen чинит; критик-проход реально улучшает результат. Это go/no-go всего проекта.

**Фаза 1 — MVP генерации (3–4 нед)**
- Prompt → Enhancer → Generator → 4 варианта в сетке. Без нод, простой UI.
- Live preview + выбор варианта. Библиотека ~20 блоков, 3 темы.

**Фаза 2 — Ноды и микс (3–4 нед)**
- React Flow граф, ноды Prompt/Enhancer/Style/Generator/Mix/Export.
- Микс с весами (сначала токены, потом структурный микс через модель).

**Фаза 3 — Редактор (4–6 нед)**
- Канвас-редактор IR: перемещение, инспектор, undo/redo.
- «Продолжить от этой версии» (diff → промпт). Critic-нода.

**Фаза 4 — Страницы и база знаний (3–4 нед)**
- Compose Page: сборка страницы из блоков разных генераций, авто-унификация токенов.
- Наполнение базы знаний (парсинг каталогов + qwen-vl разметка), RAG в Enhancer.

**Фаза 5 — SaaS-обвязка (2–3 нед)**
- Auth (Clerk/Auth.js), проекты/команды, биллинг (Stripe, токены генераций), экспорт, публичные шаблоны графов.

**Фаза 6 — Pixel-perfect reproduction (2–3 нед)**
- Нода Reproduce в нодовом графу: скриншот на входе → VLM (GLM glm-4v) анализ структуры → Python-измерения (цвета из пикселей, bounding boxes, ASCII-матрицы углов) → извлечение иконок/контента как PNG base64 → сборка HTML с absolute positioning → native screenshot (Playwright) → pixel diff по регионам → итеративная доводка до diff < 5%.
- Интеграция с Design IR: конвертация reproduction-HTML → IR (токены из измеренных цветов, дерево из структуры VLM).
- Comparison UI: 3 режима (Stacked, Side by side, Diff overlay) с метриками.
- Алгоритм задокументирован: [docs/PIXEL-PERFECT-ALGORITHM.md](docs/PIXEL-PERFECT-ALGORITHM.md).

## 9. Риски и решения

| Риск | Решение |
|---|---|
| Модель выдаёт «разномастный» дизайн | Закрытая библиотека блоков + токены; модель выбирает и стилизует, не изобретает |
| Невалидный JSON от LLM | JSON mode (Qwen) + схема-валидация + repair loop |
| Микс весов — «магия», которая не работает | Начать с детерминированного микса токенов (интерполяция OKLCH); структурный микс — отдельный эксперимент |
| Стоимость генераций | Дешёвый qwen-flash/coder для черновиков, Kimi только для финальных вариантов; кэш промптов |
| Парсинг сайтов — юридика | Только публичные метаданные/теги и собственный анализ; не хранить чужой код |

## 10. Предложения (мои дополнения)

1. **Начать с вертикали**: не «любой дизайн», а лендинги (SaaS/продукты) — самый предсказуемый и монетизируемый сегмент, блоковая структура идеально ложится на IR.
2. **«Style DNA»**: у каждой генерации сохранять вектор стиля; пользователь сможет «залочить» стиль и гонять только структуру — главный механизм консистентности.
3. **Пресеты графов**: готовые нодовые графы-шаблоны («Лендинг за 3 шага», «A/B 8 вариантов hero») — снижают порог входа в нодовый UI.
4. **Токен-бюджет как фича**: показывать стоимость ноды до запуска (как в ComfyUI видно VRAM).
5. **Экспорт в Figma позже**: сначала код (HTML/React+Tailwind) — это ценность для разработчиков уже в MVP; Figma-плагин — отдельный большой эпик.
6. **Метрики качества**: внутренний бенчмарк — 50 эталонных брифов, оценка валидности IR + скор критика; гонять при смене моделей/промптов.
