# Конкуренты: Pencil, Paper, Open Design, Figma + Claude Code — разбор и ТЗ для DesignDNA

Дата: 2026-09-04. Источник: видео «Figma больше не нужна? Тест Pencil, Paper, Open Design и Claude Code», канал «Даниил Шишко x Pixel Perfect | AI в Дизайне» (26 мин, https://www.youtube.com/watch?v=Ck9JEMEGd7c). Разбор сделан по автоматическим субтитрам и описанию ролика; тайм-коды указаны для проверки.

## 1. Что тестировал автор

- Одна задача: 5 экранов банковского приложения «Onda», флоу «спорная операция» (списание → что не так → заморозить карту → заявление → статус).
- Одна дизайн-система (собрана ранее в Figma и в коде прототипа), один и тот же промпт.
- Четыре инструмента: Pencil (десктоп, агент внутри), Paper (облако, дизайн = код), Open Design (open-source аналог Claude Design, 160+ скиллов), Figma + Claude Code через MCP.
- Автор — практик с выстроенной «агентской средой» (Claude Code, папка проекта, скиллы, MCP Mobbin/Hixfield). Его критерии: консистентность с ДС, контроль над агентом, встраиваемость в пайплайн, цена.

## 2. Пять выводов автора, которые важнее оценок конкретных инструментов

1. **Ловушка MCP «инструмент как руки» (1:22–3:49, 6:07).** Когда внешний агент (Claude Code) подключается к приложению по MCP, он видит низкоуровневые команды и использует приложение как исполнителя, игнорируя его внутренние скиллы и вкус. Результат — «очень дефолтно». Исключение — Open Design: его скиллы автоматически подхватываются при вызове через MCP (19:58).
2. **Ошибка метода (0:14).** В первой итерации автор получил три копии одного результата: он сравнивал свой промпт, а не инструменты. Пришлось для каждого инструмента задействовать его внутренний агент.
3. **Дизайн-система решает (6:49–7:40).** Без ДС любой инструмент даёт «воздух, лишние отступы, ни одного компонента». С ДС + готовыми экранами рядом + вызовом изнутри — результат «взрослый, аккуратный, можно забирать».
4. **Консистентность ломается на масштабе (10:18–11:19).** Даже сильный агент Pencil расползается: line-height 130/135, веса medium/regular вперемешку, забывает существующие экраны. Нужна доработка «ещё раз через Claude» перед использованием.
5. **Контроль важнее креатива (14:18–16:32, 22:16–23:43).** Прозрачная среда (Figma + Claude Code) даёт предсказуемый результат без потолка, зависимость «компонент в проде ↔ компонент в макете» устанавливается один раз. Цена — сложная настройка, «грабли», две платные подписки.

## 3. Плюсы и минусы инструментов

### Pencil (5:57–14:42)

Плюсы:
- Бесплатный. Сильный внутренний агент со своими скиллами.
- С ДС и референсными экранами собирает приятные, осмысленные экраны, кнопки через компоненты, повторяемое сам выносит в компоненты.
- Параллельные агенты, несколько вариантов по одному промпту, стилистические вариации по лейауту и графике.
- Импорт своей библиотеки (.pen-файл) работает.

Минусы:
- Нет вариантов компонентов: каждая вариация = новый компонент, ДС раздувается.
- Нет текстовых стилей: размер, скругление и пр. задаются токенами в каждое поле отдельно; изменить всё разом нельзя.
- Дрейф консистентности между экранами; агент забывает контекст по мере роста числа экранов.
- Чёрный ящик: скиллы не видны, правила задать нельзя, настройки «декоративные».
- Библиотеку нужно заново искать на диске при каждом запуске.
- Нельзя закинуть свой стиль и попросить декомпозировать его в библиотеку; только предустановленные стили.
- Через MCP из Claude Code даёт слабый результат; сами разработчики советуют MCP только для переноса в код.

### Figma + Claude Code через MCP (14:42–16:47, 22:16–23:59)

Плюсы:
- Полная прозрачность и контроль: агент в твоей папке, скиллы и память твои, «потолка нет».
- Зависимость между кодом и компонентами Figma устанавливается один раз; дальше агент переиспользует компоненты и токены точечно, не читая всю Figma.
- Максимальная консистентность и повторяемость; экраны совпадают с существующими по паттернам.
- Расширяемость другими MCP: Hixfield (иконки, картинки), Mobbin (референсы).

Минусы:
- Сложно поднять и настроить; нужно «понаступать на грабли».
- Платная Figma (студенческая 400 ₽ за полгода) плюс обязательная подписка Claude.
- Экраны проще и менее креативные, чем у Pencil/Open Design.
- Нет собственного «вкуса» у среды — качество упирается в то, что пользователь сам собрал в скиллах.

### Paper (17:02–19:29)

Плюсы:
- Шейдеры и эффекты, генерация картинок и иконок, пачка фреймов с текстом для рекламных креативов.

Минусы:
- Экраны «максимально простые», ни одного компонента, потому что компонентов как сущности нет.
- Вкладка «Тема» с токенами бессмысленна без компонентов.
- Нет внутреннего чата с агентом; всё только из окна Claude — неудобно для мелких правок.
- Бесплатных лимитов не хватает: агент начал один экран и попросил оплату.
- В «креативном» режиме — слоп, правил не придерживается.
- Автор не понимает, для кого этот инструмент.

### Open Design (19:29–21:48, 24:15–24:49)

Плюсы:
- Бесплатный и открытый. 160+ скиллов подхватываются автоматически при вызове через MCP.
- Следует ДС, группирует по смыслу, собирает компонентную базу.
- Отлично декомпозирует существующие ДС и чужие решения (через Mobbin MCP собрал целую ДС: иконки, кнопки, вариации), потом это перенесено в Figma.
- Умеет 3D в макете, прототипы, слайд-шоу, «живую версию продукта». Работает из коробки.

Минусы:
- Нельзя править руками: ничего не подвинуть, компоненты не видны; только через чат с агентом.
- Из-за этого нужен дорогой план или несколько моделей (Claude 5x + Codex за $20 для точечных правок).
- Промахи с отступами.
- Нет защиты от копирования чужих сайтов (автор подаёт как плюс, для продукта это риск).

### Матрица

| Критерий | Pencil | Paper | Open Design | Figma + Claude Code |
|---|---|---|---|---|
| Цена | бесплатно + подписка на модель | платно | бесплатно + подписка на модель | Figma + Claude |
| Качество экранов с ДС | высокое | низкое | высокое | среднее, но точное |
| Консистентность с ДС | средняя, дрейф | нет | средняя-высокая | высокая |
| Варианты компонентов | нет | нет компонентов | не видны | есть (Figma) |
| Текстовые стили | нет | нет | не видны | есть |
| Ручное редактирование | да | да | нет | да |
| Прозрачность агента | чёрный ящик | чёрный ящик | скиллы открыты | полная |
| Работа по MCP снаружи | «как руки» | «как руки» + лимиты | со скиллами | основной режим |
| Порог входа | низкий | низкий | низкий | высокий |

Итог автора: «быстро и красиво для себя» — Pencil; «креатив, 3D, прототип, живой продукт» — Open Design; «креативы с эффектами» — Paper (сомнительно); «полноценный продукт, точность, повторяемость» — только Claude Code + Figma. Эксперт комбинирует инструменты.

## 4. Где DesignDNA сейчас относительно этих выводов

По коду и докам ветки `codex/unified-motion-design` (см. `docs/DESIGN-STUDIO-V3.md`, `docs/IMPROVEMENT-PLAN.md`, `design-qa.md`).

Уже сильные стороны:
- **Редактируемое ядро Design IR** плюс DNA-редактор (слои, инспектор, интент-локи, undo/redo) — закрывает главный минус Open Design (нельзя править руками) и при этом сохраняет генерацию.
- **Source Import → Design System** с мастерами, наблюдёнными вариантами (`variants` в `design_system/document.py`), fidelity-метрикой, AI-ревью и AI-доводкой мастеров, `siteBrief` и режимом встраивания. Это то, что автор делал вручную через Open Design + Mobbin + Figma.
- **Токены v2 с ролями цвета и типографики** — основа для «текстовых стилей», которых нет в Pencil.
- **Vision-судья по пикселям** (Quality Pass, рубрика, порог 80) и детерминированный `qualitygate` — у конкурентов такого цикла нет вообще.
- **Арт-дирекция**: чипы направлений, варианты как разные направления, 10 эталонов.
- **Работа на консольных аккаунтах Codex CLI / Claude Code без API-ключей** и локальный десктоп — цена как у Pencil/Open Design.
- **MCP-сервер** уже есть (`designdna_mcp_server.py`).

Разрывы, которые видео делает очевидными:
1. **Наш MCP — ровно «руки».** Инструменты: `project_get`, `project_put`, `design_ir_validate`, `project_summary`, `live_command`. Внешний Claude Code получит сырой JSON проекта и будет собирать IR сам, без нашей арт-дирекции, эталонов, ДС-констрейнов и судьи. Это тот случай, за который автор ругает Pencil и Paper.
2. **Нет «скиллов» как видимой сущности.** Правила живут в `app/prompts/DESIGN.md`, `BLOCKS.md`, `RUBRIC.md`, но пользователь их не видит и не редактирует из приложения; нет журнала решений агента. Это претензия к Pencil («чёрный ящик»).
3. **Экраны приложений и флоу из нескольких экранов.** Генератор и эталоны заточены под страницы 1440; артборды мобильного приложения, флоу «экран → экран» и общая память о существующих экранах не оформлены. Тестовая задача видео — именно это.
4. **Консистентность между экранами не проверяется.** Судья и гейт работают на одну страницу; дрейф line-height/весов между экранами (главный «минус» Pencil) у нас никто не ловит.
5. **Варианты компонентов как матрица свойств** (состояние, размер, тема) — сейчас варианты наблюдённые (из источника); авторских вариантов и текстовых стилей как редактируемых сущностей в панели ДС нет.
6. **Мост с Figma и кодом.** Нет импорта ДС из Figma и экспорта в Figma; «зеркало компонент в проде ↔ в макете» есть только через Tailwind-проекцию.
7. **Внешние MCP внутрь генератора** (иконки, картинки, референсы) не подключаются.

## 5. ТЗ: чем DesignDNA будет лучше каждого из четырёх

Позиционирование: **«агент со скиллами Open Design, ручное редактирование и ДС Figma, консистентность связки Claude Code + Figma, без её настройки и без чёрного ящика Pencil»**. Ниже эпики с приоритетом, требованиями и критериями приёмки. Обозначения: P0 — нужно для победы в сравнении по методу автора; P1 — усиливает; P2 — задел.

### E1. MCP со скиллами, а не «руками» (P0)

Требования:
- Новые высокоуровневые инструменты MCP поверх существующих: `designdna_generate_screens` (бриф + ссылка на ДС + референсные экраны → N экранов через полный пайплайн арт-дирекция → композиция → гейт → судья), `designdna_apply_design_system`, `designdna_list_components` (мастера, варианты, токены, текстовые стили в компактном виде), `designdna_review` (вердикт судьи с замечаниями по экрану), `designdna_edit_scoped` (правка только выбранной ноды/секции по intent-локам), `designdna_create_variant`.
- Описания инструментов написаны так, чтобы агент предпочитал их низкоуровневым `project_put`; `project_put` помечается как «служебный, для переноса».
- Пакет скиллов для внешних агентов: `skills/designdna/SKILL.md` для Claude Code, Codex, Cursor (по образцу open-pencil/skills) — как вызывать ДС, как не ломать токены, когда звать судью.
- Единый источник правил: те же `DESIGN.md`/`RUBRIC.md`, что использует нода, попадают в MCP-ответы как контекст.

Приёмка:
- Один и тот же промпт из Claude Code через MCP и из ноды Генератора внутри приложения даёт оценку судьи с разницей ≤ 5 баллов, обе ≥ 80.
- ≥ 90 % элементов сгенерированных экранов — экземпляры мастеров ДС (метрика `components-reuse`).

### E2. Дизайн-система первого класса: варианты, текстовые стили, DS-lint (P0)

Требования:
- Варианты компонента как матрица свойств (state × size × theme × …), а не отдельные компоненты; авторские варианты создаются в панели ДС и агентом; наблюдённые варианты из Source Import мапятся в матрицу.
- Текстовые стили = роли типографики токенов v2 как редактируемые сущности (display, h1…, body, caption): семейство, вес, кегль, line-height, letter-spacing, адаптивные значения. Изменение стиля распространяется на все экраны проекта.
- **DS-lint**: детерминированная проверка «значение не из токена» (цвет, кегль, line-height, радиус, отступ), «вес вне роли», «компонент не из ДС при наличии подходящего мастера». Отчёт в панели Quality, автопочинка «привести к ближайшему токену».
- Генератор получает ДС не как текст, а как жёсткие констрейны (уже частично: `coerce_ir_tokens`); в промпт добавляется запрет сырых значений.

Приёмка:
- На 5 экранах флоу DS-lint = 0 нарушений после автопочинки; вручную внесённые 10 нарушений находятся все.
- Изменение line-height роли body в панели ДС меняет его на всех экранах за одно действие.

### E3. Флоу приложений: мобильные артборды, реестр экранов, память (P0)

Требования:
- Пресеты артбордов (390×844, 1440×900, 768×1024) и нода **Flow**: цепочка экранов с переходами; генерация «следующего экрана» видит все существующие экраны флоу (компактный дайджест + миниатюры) и референсные экраны, переданные пользователем («рядом положил экраны, сделай так же»).
- Реестр экранов проекта: имена, назначения, использованные мастера — источник контекста для агента вместо «забыл, с чего начинали».
- Эталоны для мобильных приложений (финтех, e-commerce, сервис) — минимум 5, оценка судьи ≥ 90.
- Экспорт флоу как кликабельного прототипа (уже есть Recorder/Motion — связать).

Приёмка:
- Тестовая задача из видео (5 экранов «спорная операция» по заданной ДС) генерируется одной командой ≤ 5 минут, медиана судьи ≥ 85, DS-lint = 0, все экраны используют одни и те же мастера шагов/кнопок/карточек.

### E4. Прозрачный агент: скиллы, правила, журнал решений (P0)

Требования:
- Панель «Правила и скиллы» в проекте: `DESIGN.md`, `BLOCKS.md`, `RUBRIC.md` и пользовательские правила редактируются в приложении, версионируются с проектом и применяются генератором и судьёй.
- Журнал решений на каждый запуск: выбранное направление и почему, применённые правила, переиспользованные мастера, созданные токены, замечания судьи и что починено. Виден в ноде и отдаётся по MCP.
- Taste-профиль проекта (уже начат в арт-дирекции) — виден и редактируется.

Приёмка:
- Каждый результат генерации сопровождается журналом; изменение пользовательского правила («никаких карточек с тенью») проходит в следующий запуск и проверяется судьёй (тест).

### E5. Паритет ручного и чат-редактирования (P1)

Требования:
- Любое изменение агентом — диф в истории IR с undo; выделение на канвасе ограничивает область правки агента («измени только эту кнопку»); интент-локи защищают неприкосновенное.
- Чат правок внутри редактора (не только в ноде) с мгновенным предпросмотром, как «пообщайся с чатиком или руками поправь», но в одном окне.

Приёмка:
- 20 типовых правок (текст, цвет, отступ, замена компонента, порядок секций) выполняются из чата с областью выделения без побочных изменений вне области (тест на диф).

### E6. Мост Figma ↔ DesignDNA ↔ код (P1)

Требования:
- Импорт ДС из Figma (REST API или Figma MCP): переменные → токены v2, компоненты и их варианты → мастера с матрицей вариантов, текстовые стили → роли.
- Экспорт экранов и ДС в Figma (через плагин или путь Claude Code → Figma) с сохранением компонентов и токенов.
- Экспорт в код: Tailwind-проекция и HTML/CSS уже есть; добавить экспорт компонентов ДС как библиотеки (React/Svelte) с теми же именами, что в макете — «зеркало прод ↔ макет».

Приёмка:
- Круговой обход 10 компонентов Figma → DesignDNA → Figma без потери токенов и вариантов; сгенерированный экран, собранный из мастеров, экспортируется в код, где каждый мастер = именованный компонент.

### E7. Библиотеки без боли (P1)

Требования:
- ДС как переносимый пакет `.ddna-kit` (токены, мастера, варианты, правила, шрифты) с версией; импорт одним действием, кит остаётся в проекте между сессиями; общий кит на несколько проектов.
- «Закинь свой стиль»: из скриншотов/сайта/PDF-гайда собирать кит (Source Import уже это делает для сайтов; добавить картинки и PDF).

Приёмка:
- Кит из проекта A подключён к проекту B за ≤ 3 действия; генерация в B использует мастера A.

### E8. Параллельные варианты и сравнение (P1)

Требования:
- N параллельных запусков по одному брифу с разными направлениями (чипы уже есть) и разными провайдерами; вид «сравнение» с оценками судьи и DS-lint; выбор и слияние (взять hero из варианта 2, шаги из варианта 1).

Приёмка:
- 3 варианта за время одного (параллельность), сравнение и слияние секций без правки JSON.

### E9. Внешние MCP внутрь генератора (P2)

Требования:
- Подключение внешних MCP-инструментов к ноде Генератора и редактору с allowlist: иконки/картинки (генерация в стиле ДС), референсы (Mobbin-подобные), контент.
- Локально-ориентированная политика: что уходит наружу, показывается пользователю (как уже сделано для видео-генерации).

### E10. Порог входа и цена (P1)

Требования:
- Онбординг «первый флоу за 10 минут»: выбрать пресет, подключить консольный аккаунт (Codex/Claude — уже есть), импортировать ДС или взять стартовый кит, сгенерировать.
- Стартовые киты (3–5) для тех, у кого нет ДС, как «предустановленные стили» Pencil, но редактируемые и декомпозируемые.
- Индикатор расхода лимитов провайдера и режим «экономно» (быстрая модель для арт-дирекции, сильная — для композиции; уже частично).

### E11. Постоянный бенчмарк «по методу автора» (P0, дешёвый)

Требования:
- Зафиксировать задачу видео как бенчмарк: ДС Onda-подобного банка (собрать свою, не копировать), 5 экранов, один промпт, референсные экраны; прогонять на каждом релизе внутренним пайплайном и по MCP из Claude Code; хранить PNG и оценки в `results/`.
- Слепая оценка судьёй наших результатов и (вручную загруженных) результатов конкурентов по одной рубрике: качество, консистентность с ДС, переиспользование компонентов, время, стоимость.

Приёмка:
- Отчёт `results/benchmark-app-flow.md` обновляется автоматически; цель на первый релиз: судья ≥ 85, DS-lint 0, время ≤ 5 мин, MCP-путь ≥ 80.

### Ограничение по этике и праву

Source Import и «декомпозиция чужих решений» (то, что автор хвалит в Open Design как «без защиты от воровства») в DesignDNA должны требовать подтверждения прав на источник или явной пометки «только для изучения»; в кит из чужого сайта не экспортируются шрифты и картинки без лицензии. Это отличие, а не слабость: продукт для команд, которым нужно отдавать результат в прод.

## 6. Порядок исполнения

1. E11 (бенчмарк) → фиксирует линейку измерений до изменений.
2. E2 (варианты, текстовые стили, DS-lint) и E3 (флоу и мобильные артборды) — параллельно, они дают самый видимый разрыв с Pencil и Open Design.
3. E1 (MCP со скиллами) и E4 (прозрачность) — превращают среду в то, что автор называет «правильно выстроенной агентской средой», но из коробки.
4. E5, E7, E8, E10 — качество жизни, закрывают оставшиеся минусы Pencil.
5. E6, E9 — мосты и расширяемость.

Ключевые метрики продукта после реализации: медиана судьи на бенчмарке ≥ 85 (внутри) и ≥ 80 (по MCP), DS-lint = 0, доля элементов из мастеров ≥ 90 %, время до первого флоу для нового пользователя ≤ 10 мин, ноль ручных «пересборок через Claude» перед передачей в код.
