## 0. Принцип: контроль = слоёная модель детерминизма

Урок Houdini: контроль даёт не количество кнопок, а то, что **каждая операция
явна, обратима и подглядываема**. Предлагаю жёстко разделить ноды на два класса
и помечать их визуально:

- **D (deterministic)** — чистые операции над IR, без LLM: предсказуемы, мгновенны,
  бесплатны. Их должно быть большинство — как SOP-ов в Houdini.
- **AI** — LLM/VLM внутри: генерация, refine, критик. Пользователь всегда видит,
  где именно в графе принимается «решение машины», и может заменить его ручной
  нодой.

Киллер-фича формулируется так: **«AI предлагает — граф фиксирует»**: любая
AI-выдача может быть заморожена, разобрана на параметры и дальше правиться только
детерминированными нодами. Чем больше D-нод в графе пользователя, тем больше контроль.

Второй урок Houdini — **типизация портов**. Сейчас типы: `text | ir`. Предлагаю
расширить (сильная типизация = предсказуемость соединений):

| Тип порта | Содержимое | Зачем |
|---|---|---|
| `text` | строка/бриф | как сейчас |
| `ir` | полный Design IR | как сейчас |
| `tokens` | только tokens (палитра/шрифты/радиусы/отступы) | Style DNA, лок стиля |
| `attrs` | «пакет параметров»: числа, извлечённые из IR/сайта (отступы, ширины, шкалы) | копирование параметров из референсов |
| `selection` | список путей IR (`secIdx/path`) | точечные операции над частью дерева |

## 1. Каталог нод

Статусы: ✅ есть · 🟡 есть частично/API без ноды · ❌ новое.
Класс: **D** — детерминированная, **AI** — с LLM.

### 1.1. Входы (источники) — в Houdini: OBJ/File

| Нода | Класс | Аналог Houdini | Статус | Назначение |
|---|---|---|---|---|
| **Prompt** | D | Text Object | ✅ | Текст задачи |
| **Reference** | AI | — | ✅ | Изображение/скриншот + описание стиля |
| **IR Import** | D | File Cache | ❌ | Вставить/загрузить готовый IR (файл, results/, галерея). Вход для «чужих» дизайнов и версий |
| **Site Probe** | D | — | 🟡 (scraper есть, ноды нет) | URL → **пакет параметров сайта**: палитра, шрифты, шкала отступов, ширина контейнера, радиусы, типографская шкала. Без LLM, см. §3 |
| **BlockParse** | D+AI | — | 🟡 (`/api/clone` есть для одного компонента) | URL → декомпозиция разметки 1-в-1 на блоки; **порты = блоки** (header, hero, pricing, footer…). См. §7 |

### 1.2. Стиль и параметры (аналог Houdini Attributes)

Это ядро киллер-фичи: всё, что позволяет **зафиксировать стиль** и гонять только
структуру/контент.

| Нода | Класс | Аналог Houdini | Статус | Назначение |
|---|---|---|---|---|
| **Style DNA** | D | Attribute Create | ❌ (в SPEC как видение) | Чистые токены без дерева. Источники: вручную / из Reference / из Site Probe / «вытащить из IR». Выход `tokens` подключается к любому генератору → **стиль залочен**, модель варьирует только структуру и контент |
| **Token Override** | D | Attribute Set | ❌ | Точечная перезапись значений токенов (primary → #0E7A5F, spacing.section → xl) без LLM — инспектор в виде ноды |
| **Attr Extract** | D | Attribute Promote/Extract | ❌ | Из любого IR вытаскивает **числовой пакет**: вертикальные отступы между секциями, контейнер, gap-ы, радиусы, шкалу шрифтов, высоты строк. Выход `attrs` |
| **Attr Transfer** | D | Attribute Transfer SOP | ❌ | Перенос `attrs`-пакета с одного IR на другой: «структура от генерации B, ритм отступов от сайта A». Детерминированно, с маппингом и предпросмотром diff |
| **Palette Ops** | D | Color SOPs | 🟡 (OKLCH-микс уже в colorutils) | Операции над цветом: сдвиг L/C/H в OKLCH, построение палитры от одного цвета (аналог/комплементарная), WCAG-контраст-чек. Контроль цвета без AI |

### 1.3. Генерация (AI-операторы)

| Нода | Класс | Аналог Houdini | Статус | Назначение |
|---|---|---|---|---|
| **Generator** | AI | — | ✅ | brief → N вариантов IR. Дополнить входом `tokens` (см. Style DNA) |
| **Refine** | AI | — | 🟡 (API `/api/refine` есть, ноды нет) | IR + инструкция → IR. Обязательная нода: без неё refine живёт вне графа |
| **Prompt Enhancer** | AI | — | ❌ (PLAN) | Слабый промпт → детальный бриф (RAG по базе знаний, когда появится) |
| **Batch / Variant** | AI | Copy to Points × time() | ❌ (PLAN) | 1 вход → N вариантов по seed/температуре/стиль-тэгам. «Дай 8 версий этой шапки» |
| **Scoped Gen** | AI | — | ❌ | Генерация **только части**: одна секция/блок по пути из `selection`, остальной IR не трогается. Ключевая нода контроля: AI работает локально |
| **Reskin** | AI | — | ❌ | **Лок структуры**: расположение элементов заморожено, AI меняет только разрешённое маской (цвета/шрифты/контент). На выходе — структура референса 1-в-1 в новой стилизации. Детерминированный merge-back гарантирует лок. См. §7 |
| **Critic** | AI | — | ❌ (PLAN) | Рендер → скриншот → vision-отчёт (контраст, сетка, иерархия) → автофикс по чекбоксу |

### 1.4. Операции над IR (SOP-слой — самый «houdini»-слой)

| Нода | Класс | Аналог Houdini | Статус | Назначение |
|---|---|---|---|---|
| **Edit (Figma)** | D | — | ✅ | Ручная правка геометрии/текстов |
| **Select / Blast** | D | Blast SOP | ❌ | Выбрать/удалить/извлечь секции по типу или пути: «убрать footer», «вытащить только hero». Выходы: `ir` + `selection` |
| **Pick Block** | D | — | ❌ | Выбор именованного блока из «пучка» BlockParse параметром (имя/индекс). Fallback-вариант, если не делать динамические порты на BlockParse |
| **Merge** | D | Merge SOP | ❌ | Склейка деревьев нескольких IR в один док (сборка страницы из блоков). Не путать с Mix: Merge = конкатенация, Mix = смешивание. Первый шаг Compose Page |
| **Switch** | D | Switch SOP | ❌ | N входов → один выход, слайдер/кнопка выбора. Переключение версий **без регенерации** — дёшево и мгновенно |
| **Transform / Layout** | D | Transform SOP | ❌ | Числовые параметры раскладки: глобальный масштаб отступов (×0.8…×1.5), плотность compact↔spacious, ширина контейнера, колонки сетки |
| **Sort / Reorder** | D | Sort SOP | ❌ | Перестановка секций (drag в мини-списке или правила: «faq всегда перед cta») |
| **Stamp / Copy** | D | Copy SOP | ❌ | **Киллер-нода «стиль на все компоненты»**: берёт блок/токены со входа A и штампует в N слотов входа B (карточки, страницы, секции). Механизм применения одной ДНК ко всему |
| **Group** | D | Groups | 🟡 (в редакторе есть, ноды нет) | Именованные selection-наборы, переиспользуемые в других нодах |

## 2. Механика «своих нод» = Houdini Digital Assets

Запрос владельца: «свои ноды можно сохранять и подавать другой промпт, чтобы
генерировалась другая версия дизайна». В Houdini это решено HDA: сеть упаковывается
в ассет, параметры внутренних нод выносятся на интерфейс ассета. Предлагаю ту же модель:

**Ассет = JSON-пакет:**
```
asset/
  manifest:  { name, version, tags, thumbnail }
  graph:     фрагмент графа (ноды + провода), как в автосейве
  params:    [{ name, type, default, boundTo: {node, field} }]  ← интерфейс
  io:        { inputs: [{port, type}], outputs: [{port, type}] }
```

- **Сохранение:** контекстное меню по выделенной группе нод → «Сохранить как ноду» →
  имя + какие поля внутренних нод выставить параметрами (галочки).
- **Использование:** ассет появляется в меню правого клика как одна нода. В неё
  подаётся **другой промпт** во вход Prompt, а запертые внутри параметры (стиль,
  провайдер, количество вариантов, структура графа) сохраняются → **новая версия
  дизайна в той же ДНК**.
- **Версионирование:** обновление внутренней сети ассета создаёт v2; инстансы держат
  ссылку на версию (как HDA versioning) — ничего не ломается.
- **Хранение:** `assets/` в данных пользователя (JSON) + встроенные пресеты проекта
  («Шапка SaaS за 3 шага», «A/B 8 hero», «Перенос отступов с сайта»). В SaaS —
  приватные ассеты команды + публичный каталог (PLAN.md §10.3).
- **Позже:** expressions — параметр ассета ссылается на параметр другой ноды
  (`$ref.spacingScale * 0.8`), как parameter expressions в Houdini.

## 3. Механика «параметры из референсного сайта» (Site Probe → Attr Transfer)

Запрос: копировать из референсных сайтов размеры, отступы и подобное.

**Принцип из pixel-perfect пайплайна (уже доказан проектом): числа — из измерений,
не из LLM.** LLM даёт только семантику («это шкала отступов»), значения считаются кодом.

**Пайплайн ноды Site Probe:**
1. URL → fetch + Playwright computed styles (всё уже в `scraper.py`);
2. Измеряются: палитра (частотный анализ цветов), шрифты + шкала размеров,
   вертикальные расстояния между секциями (по bounding boxes), ширина контейнера,
   радиусы, gap-ы сеток;
3. Кластеризация отступов → **шкала** (например 8/16/24/48/96) и dominante-значения;
4. Выходы: `tokens` (готовый Style DNA) + `attrs` (числовой пакет) + текстовый бриф.

**Применение:** `attrs` → вход **Attr Transfer**, второй вход — целевой IR.
Результат: структура и контент свои, а ритм/отступы/радиусы — с референса.
Перед применением — нода **Compare**, чтобы видеть, что именно поменяется.

## 4. Приоритизация (рекомендация)

Порядок под киллер-фичу «максимальный контроль» и решения владельца
(React Flow сейчас; экспорт №1 после ядра; артефакты — код + дизайн-док):

| Волна | Ноды | Почему именно они |
|---|---|---|
| **1. Контроль стиля** | Style DNA, Token Override, вход `tokens` в Generator | Минимальный набор «стиль заперт, AI варьирует только структуру» — суть обещания |
| **2. Параметры из референсов** | Site Probe, Attr Extract, Attr Transfer | Прямой запрос владельца; использует готовый scraper |
| **2.5. Референс 1-в-1** | BlockParse, Reskin | Пайплайн «понравился сайт» (§7): декомпозиция на блоки + рестайл с локом структуры. Опирается на готовый `/api/clone` |
| **3. Сборка без AI** | Blast, Merge, Switch, Refine-нода | Детерминированная сборка страницы; заносит refine в граф |
| **4. Свои ноды** | Subnet, Asset (HDA) с параметрами | Прямой запрос владельца; требует стабильного формата графа после миграции |
| **5. Контроль изменений** | Compare/Diff, Inspect, Critic | «Видеть, что изменилось» — контроль версии |
| **6. Выход** | Export Code + дизайн-док | Артефакт для монетизации (решение владельца) |

Между волнами: порт-типы (`tokens`, `attrs`, `selection`) и bypass-флаг на любой
ноде — заложить в контракт React Flow сразу (Фаза B миграции).

## 5. Конвенции UX из Houdini, которые стоит перенести

1. **Цвет нод по категории:** GEN — фиолетовый, STYLE — зелёный, EDIT/SOP — синий,
   FLOW — оранжевый, OUT — жёлтый, AI-ноды — значок ✦/молния.一眼 видно, где AI.
2. **Bypass** (флаг на любой ноде) — выключить ноду, не разрывая провода.
3. **Middle-click** по ноде — быстрые параметры (как в Houdini).
4. **Бейдж версии результата** на выходе ноды + Null-кэш для тяжёлых пайплайнов.
5. **Провода подписаны типом** при наведении (`ir`, `tokens`, `attrs`…).
6. **Оранжевая рамка у «готовящейся» ноды** (в Houdini — cooking state).

## 7. Пайплайн «понравился сайт»: BlockParse → Reskin → Edit/Export

Сценарий (идея владельца, 2026-08-05): нравится сайт → отдельная нода 1-в-1
разбирает дизайн и берёт из кода разметку → после анализа внутри ноды появляются
**параметры = блоки** (header, hero, …) → к параметру `header` подключается
следующая нода → блок уходит либо в **редактор**, либо в **AI-ноду с локом
структуры** → на выходе структура, идентичная референсу, но изменённая AI
(цвета, стилизация) → дальше редактировать или экспортировать в код.

```
BlockParse(url) ──┬─ header ─→ Reskin(лок структуры; стиль: промпт/DNA) ─→ Edit ─→ Export Code
                  ├─ hero ───→ (своя ветка: Editor / другая генерация)
                  └─ tokens ─→ Style DNA ─→ в другие генераторы
```

### 7.1. BlockParse

- **Класс:** D+AI (детекция и измерения детерминированные, LLM — на воспроизведение блоков).
- **Вход:** URL (+ опционально список нужных блоков, чтобы не клонировать всё).
- **Шаги:**
  1. fetch + computed styles — `scraper.py` (есть);
  2. детерминированная детекция границ блоков: семантические теги, секции/заголовки —
     `extract_structure` (есть частично); результат — список `{name, selector}`;
  3. каждый блок → IR через механизм `/api/clone` (есть; режим edit = точное
     воспроизведение) — параллельно, ThreadPool как в generate;
  4. кэш в sqlite (есть для clone/reproduce) — повторный разбор сайта бесплатен.
- **Выходы (утверждено владельцем):** динамические порты — после анализа нода
  показывает список блоков с миниатюрами, пользователь «зажигает» нужные, под
  каждым появляется выход `ir`. Плюс постоянный выход `tokens`. Pick Block —
  только как вспомогательная нода для программного выбора (не основной UX).
- **Vision-fallback** для canvas/JS-сайтов, где нет семантической разметки
  (механика vision-decompose).
- **Важно:** цель — точь-в-точь, а не «похожее»; это отличает BlockParse от
  Site Probe (который измеряет параметры, но не восстанавливает структуру).

### 7.2. Reskin (AI с локом структуры)

Название **утверждено владельцем**: Reskin (отброшены: Restyle, Repaint, StyleLock).

- **Класс:** AI.
- **Входы:** `ir` (блок) + опционально `tokens`/`text` (источник нового стиля) + текстовый промпт.
- **Маска лока** (чекбоксы):
  - структура и геометрия (топология дерева, frame, разметка props) — **залочены всегда**;
  - что разрешено менять: цвета / шрифты / радиусы / тени / тексты / картинки —
    выбирает пользователь.
- **Ключевой механизм — детерминированный merge-back.** Модель НЕ обязана сохранить
  структуру сама: после её ответа программа **принудительно возвращает залоченные
  поля из входного IR** (topология + frame + props-разметка), а из ответа модели
  берёт только поля из разрешённой маски. Дрейф структуры невозможен конструктивно —
  это и есть «максимальный контроль»: гарантия, а не просьба к модели. Попытки
  модели тронуть залоченное — молча перезаписываются и пишутся в лог ноды.
- Валидация по схеме + repair — как обычно.
- **Advanced:** слайдер силы лока (как denoising strength в img2img):
  «полный лок» → «разрешить только отступы» → «структура примерно». Для v1 — чекбоксы.
- Детерминированный аналог без AI: Token Override + Attr Transfer («рестайл без
  генерации») — уже в каталоге; Reskin = AI-версия с промптом.

### 7.3. Что уже есть в коде (оценка задела)

| Кусок | Статус |
|---|---|
| Fetch + computed styles сайта | ✅ `scraper.py` |
| Детекция блоков (navbar/hero/sections/footer) | 🟡 `extract_structure` |
| Воспроизведение одного блока 1-в-1 | ✅ `/api/clone` (режим edit + repair) |
| Токены сайта | ✅ `parse_design_tokens` |
| Кэш повторов | ✅ `cache_store.py` |
| Параллельный clone всех блоков = BlockParse-бэкенд | ❌ (обвязка над готовым) |
| Merge-back залоченных полей | ❌ (новое; небольшой utility: diff-маска по схеме) |
| UI-ноды | ❌ — после миграции React Flow; прототип механики возможен на legacy |

### 7.4. Замечания

- **Юридика:** пайплайн копирует чужие сайты 1-в-1 → действует решение владельца
  «только свои сайты» (§6.1 B2B-оценки): в ToS запрет чужих сайтов, в UI —
  подтверждение «это мой сайт».
- **Стоимость:** clone каждого блока = LLM-вызов; кэш + опциональный список блоков
  сдерживают расход. Для гибридной монетизации: BlockParse = N кредитов (по числу блоков).

### 7.5. Решения владельца по пайплайну (2026-08-05)

1. **Название AI-ноды с локом структуры: Reskin** (отброшены Restyle, Repaint, StyleLock).
2. **Выходы BlockParse: динамический порт на каждый блок** (пользователь «зажигает»
   блоки после анализа). Pick Block — только вспомогательная нода, не основной UX.
3. **Тайминг: бэкенд сейчас, ноды после миграции React Flow.** Состав бэкенда
   (независим от фронта, делается в Python-слое):
   - параллельный clone всех/выбранных блоков сайта поверх `/api/clone` (ThreadPool,
     кэш в `cache_store`, ошибки поодиночке не роняют остальные — паттерн `/api/generate`);
   - детекция границ блоков (допилить `extract_structure` в `scraper.py`);
   - **merge-back utility**: по маске лока возвращает залоченные поля из входного IR
     после ответа модели (топология дерева, frame, props-разметка); покрыть unit-тестами;
   - эндпоинты: `POST /api/block-parse` (`{url, blocks?}` → список блоков-IR + tokens)
     и `POST /api/reskin` (`{ir, prompt?, tokens?, mask}` → IR, структура гарантирована);
   - валидация по схеме + repair — существующий паттерн.
   UI-ноды BlockParse/Reskin подключаются на React Flow после переключения `/` (Фаза C).

## 8. Фичи «следующего уровня» киллер-фичи — УТВЕРЖДЕНО владельцем (2026-08-05)

Логика: §7 даёт контроль над **структурой** («AI не сломает референс»). Следующий
уровень — контроль над **правилами, исследованием и временем**: пользователь
задаёт инварианты, система сама их охраняет; исследование вариантов — параметрами,
а не рулеткой промптов; каждое состояние обратимо; продукт учит вкус пользователя.

### 8.1. Constraints — инварианты, которые AI не может нарушить

Аналог Houdini: Constraint SOP / RBD. **Декларативные правила поверх IR**,
которые выполняются детерминированным решателем после **любого** изменения —
от модели или от руки:

- «контраст text/background ≥ 4.5 (WCAG AA)», «все отступы кратны 8»,
- «кнопки в блоке одинаковой ширины», «faq всегда перед cta», «не более 2 шрифтов».
- Нарушение → авто-доводка решателем (без LLM) + бейдж «правило N починило X».

Почему киллер: контроль переходит от «проверить после» к «невозможно сломать».
Задел: snap 8px уже есть; WCAG-контраст считается из токенов; правила — JSON рядом с IR.

### 8.2. Wedge — параметрический свип вариантов

Аналог Houdini: Wedge node (parameter sweep). Берём ноду (Generator/Reskin/Mix),
задаём 2–3 параметра с диапазонами — палитра ×3 стиля, плотность ×3, радиусы ×2 —
и нода автоматически прогоняет все комбинации (3×3 = 9 результатов) и выкладывает
сеткой с превью. Выбор победителя — нодой Switch.

Почему киллер: исследование дизайна **параметрами**, а не угадыванием промптов;
каждая ячейка сетки объяснима («это вариант с плотностью compact и тёплой палитрой»).
Задел: Batch/Variant + Switch + ThreadPool из generate. Стоимость: N = произведение
диапазонов → обязателен лимит кредитов на свип (монетизация: свип = пакет).

### 8.3. Quality Gate — «тесты для дизайна»

Аналог Houdini: COPs-проверки / тесты рендера. Детерминированный линтер IR +
рендер-проверки, через который проходит каждый результат: контраст, сетка 8px,
иерархия (один h1, шкала заголовков), ритм отступов, overflow за границы фрейма.
Зелёный/красный бейдж на выходе ноды; опционально — нода не пропускает дальше.

Почему киллер: «дизайн, который проходит проверки» — язык, понятный B2B (как CI
для кода); отличает от v0/Lovable, где качество — лотерея.
Задел: рендерер + Playwright уже есть; проверки пишутся как правила (см. 8.1).
Связка: Quality Gate (детерминированный) + Critic (vision) = двухслойный контроль.

### 8.4. Timeline / Design Git — версионирование графа

Каждый результат ноды иммутабелен и кэшируется по content-hash (sqlite-кэш уже
есть), граф имеет полную историю: ветвление («попробовать другое направление от
этой версии»), откат к любому состоянию, Compare любых двух версий (§1.5).

Почему киллер: контроль = уверенность, что ничего не потеряется; «git для дизайна»
внутри нодового графа. Для команд (B2B) — основа совместной работы позже.
Задел: irhistory (undo), avтосейв графа, content-hash-кэш.

### 8.5. Taste Memory — продукт учит вкус пользователя

Закрывает два разрыва из README/SPEC (авто-diff геометрии → промпт 🟡, Style DNA ❌):

1. **Авто-diff → промпт:** ручная правка пользователя автоматически сериализуется
   в описание («увеличил отступы секций, кнопки pill, палитра теплее») и подмешивается
   в следующие генерации — без ручного промптинга.
2. **Профиль вкуса:** накопленные пары «было → отредактировано» образуют профиль
   предпочтений (few-shot контекст / RAG). Чем дольше работаешь — тем точнее
   генерации «сразу в точку».

Почему киллер: retention-moat — переключение на конкурента = потеря накопленного
вкуса. Усиливает главную ценность: «максимальный контроль» превращается в
«минимум контроля со временем — система уже знает, что вы любите».
Риск: приватность (история правок в облаке) — нужен opt-in и «локальный режим».

### 8.6. Позже (зафиксировано, не приоритет)

- **Style Space (CHOPs-аналог):** непрерывные слайдеры стиля (плотность/температура
  цвета/«строгость») с интерполяцией между DNA — развитие Mix в стиле-пространстве.
- **Style Compositor:** веса на уровне отдельных атрибутов (отступы от сайта A 60%,
  палитра со скриншота B, типографика от сайта C) — расширение Attr Transfer.
- **Роли/права на лок** (B2B): контент правят джуны, токены — лиды, структура — только
  система. Связывается с решениями по командам из B2B-ASSESSMENT.

### 8.7. Рекомендуемый порядок (моё мнение)

1. **Quality Gate + Constraints** (общий механизм правил) — дёшево, детерминированно,
   сразу усиливает киллер-фичу «контроль» и продаваемо в B2B.
2. **Wedge** — вау-эффект исследования; опирается на готовые куски.
3. **Timeline** — инфраструктура надёжности; растёт из кэша постепенно.
4. **Taste Memory** — самый сильный moat, но требует накопленной базы правок и
   аккуратной приватности; запускать после первых платящих.

### 8.8. Решения владельца (2026-08-05)

1. **В каталог берутся все пять фич**: Constraints, Wedge, Quality Gate, Timeline,
   Taste Memory — как бэклог с порядком из §8.7.
2. **Первым после бэкенда пайплайна BlockParse/Reskin идёт механизм правил
   Quality Gate + Constraints** (общая инфраструктура правил поверх IR).
3. **Taste Memory: opt-in + локальный режим.** Обучение на правках включается
   пользователем явно; в локальном режиме профиль вкуса не покидает машину.
   Позиция фиксируется в ToS и в onboarding — это аргумент в B2B security-ревью.
4. **Wedge в v1: до 3×3 = 9 генераций** (два параметра × три значения),
   с обязательным лимитом кредитов на свип и видимостью стоимости до запуска
   (токен-бюджет, PLAN.md §10.4).

## 9. Headless / Design API — ПРЕДЛОЖЕНИЕ (ждёт решения владельца)

Наблюдение: первичный сегмент (решение из B2B-ASSESSMENT §6.1) — **AI-разработчики
и соло-фаундеры**. Их естественный способ потребления инструментов — не UI, а API.
Предложение: дать продукту **второй вход — программный**.

### Суть

Любой сохранённый граф/ассет (§2 HDA) публикуется как эндпоинт:

```
POST /v1/run/{asset-id}
{ "prompt": "шапка для финтех-лендинга", "params": { "tone": "dark-premium" } }
→ { "ir": {...}, "previewUrl": "...", "code": { "html": "..." } }
```

- Ассеты = «функции дизайна» с параметрами; пользователь сам решает, что выставить наружу.
- Встроенные публичные ассеты: `landing-from-brief`, `reskin-url`, `style-dna-from-site`.
- Результаты — IR + (после Export Code) код; тот же кредитный биллинг.

### Почему это усиливает киллер-фичу и бизнес

1. **Дистрибуция через сегмент:** AI-разработчики встраивают генерацию дизайна в свои
   продукты/пайплайны (как Replicate для моделей) — каждый интеграционный вызов =
   использование платформы, а не разовый визит в UI.
2. **Контроль не теряется, а масштабируется:** ассет публикуется вместе с локами
   и правилами (Constraints/маски Reskin внутри) — вызывающий получает вариативность
   только в разрешённых пределах. «Контроль как API-контракт».
3. **Монетизация:** API-вызовы = кредиты (гибридная модель уже утверждена);
   отдельные тарифы для интеграций.
4. **Тестирует рынок раньше UI:** API-бета для разработчиков может выйти до полной
   полировки фронтенда.

### Задел и стоимость реализации

| Кусок | Статус |
|---|---|
| Эндпоинты-операции (generate/refine/mix/clone/block-parse/reskin) | ✅/🟡 — ядро уже API |
| Формат ассетов с параметрами (§2) | ❌ — сначала HDA-механика |
| Auth/API-ключи/квоты | ❌ — общая SaaS-обвязка |
| Рендер превью по требованию | 🟡 Playwright есть |

Вывод: API-режим почти бесплатен поверх HDA + SaaS-обвязки; отдельная большая
работа не нужна — нужно заложить в формат ассета (§2) поле `api: {published, params}`
и не ломать его при эволюции.

### 9.1. Решение владельца (2026-08-05)

**Headless/Design API берём в каталог; приоритет — после SaaS-обвязки** (auth/биллинг).
Обязательство на сейчас: в формат ассета (§2) сразу заложить поле
`api: { published: bool, params: [...] }` и не ломать его при эволюции формата,
чтобы публикация ассетов эндпоинтами не потребовала миграции данных.

## 10. Рынок ассетов — ПРЕДЛОЖЕНИЕ (продолжение §2 и §9)

Когда ассеты сохраняются (§2) и публикуются как API (§9), естественный следующий
шаг — **каталог ассетов**:

- публичные графы-шаблоны (PLAN.md §10.3): «Лендинг за 3 шага», «A/B 8 hero»,
  «Reskin моего сайта»;
- автор получает % с кредитов, потраченных на запуск его ассета (кредитная модель
  уже утверждена — механика простая);
- для сегмента AI-разработчиков: ассеты как «модели на Replicate» — репутация,
  форки, версии.

Это превращает продукт из инструмента в **платформу** — классический переход
инструмент → маркетплейс с сетевым эффектом. Стоимость: хранение/версионирование
ассетов + рейтинг/модерация; откладывать до появления первых пользовательских ассетов.

### 10.1. Решение владельца (2026-08-05)

**Рынок ассетов фиксируется как долгосрочное видение платформы.** Практическое
следствие на сейчас: формат ассета (§2) проектировать с учётом публикации
(метаданные: имя/теги/автор/версия/лицензия + `api{}` из §9.1), чтобы каталог
ассетов строился без миграции. Реализация — после появления первых
пользовательских ассетов.

## 11. Конвейер расширения библиотеки блоков — УТВЕРЖДЕНО (2026-08-05)

Проблема: закрытая библиотека (~19 типов секций, `docs/BLOCKS.md`) — это
консистентность, но и потолок разнообразия: у платящих быстро возникнет ощущение
«всё выглядит одинаково».

**Решение владельца: расширение через LLM-конвейер + валидацию.** Механика:

1. Модель по брифу («нужен блок comparison с таймлайном») генерирует кандидата:
   тип/вариант + schema-фрагмент props + правила композиции;
2. прогон через схему (`design-ir.schema.json`) и **рендер-проверку** (блок
   рендерится без overflow/поломок — инфраструктура Quality Gate, §8.3);
3. ревью (оркестратор/владелец) → включение в `docs/BLOCKS.md` и системный промпт
   (`build_system_prompt()`).

Связь: конвейер использует Quality Gate как приёмочный фильтр; в перспективе —
запросы новых блоков от пользователей (кредитная модель мотивирует: блок,
которым пользуются, приносит ценность платформе).
