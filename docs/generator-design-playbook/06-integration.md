Правила компаний используются как методы: Material — роли и доступность; Gravity — плотные рабочие интерфейсы; Alfa — формы; Airbnb — принятие решения; Meta — последовательность действий; Cian — поиск и сравнение; AI kits — состояния AI-интерфейса. Это не копирование брендовых оболочек. Mobbin flows не были получены: runtime прямо сохраняет это ограничение. React/UI kits не устанавливаются в Svelte-приложение; используются семантика и patterns, доступные Design IR.

## 2. Поведение ноды

В «Задача и направление» доступны автоматическое определение или явный тип: лендинг, каталог, карточка, оформление, аналитика, форма, редактор, AI-интерфейс, статья, лента, компонент. Явный выбор важнее эвристики текста. Смена сценария очищает предыдущие арт-направления.

Без DS доступны 16 стилевых направлений и автоматический выбор. С подключённой DS поле стиля отключено: внешность задаёт система. Tokens-only также фиксирует основы, даже если стиль был сохранён ранее. Предпочтение стиля не отменяет пользовательский scope редактирования.

Лендинг без фиксированных foundations использует существующую генерацию арт-направлений, теперь с новой policy. Для остальных сценариев используются три плана композиции: задача, сравнение, последовательное решение. Это внутренние `generator-plan/1.0` records; они не добавляются в старую закрытую `design-brief/1.0` schema и не притворяются DesignBrief. В strict допустимо одно направление — композиция зарегистрированных мастеров.

## 3. API и двухфазность

Новые необязательные поля `GenerateReq`:

```json
{
  "surface": "auto",
  "designStyle": "auto",
  "preparedContextId": null,
  "allowStrictFallback": false
}
```

`prepareOnly` возвращает промпты, направления и `preparedContextId`. Нода возвращает этот ID вместе с `rawOutputs`. Сервер проверяет исходные параметры, разрешённую DS-ревизию, hash политики, файлы промптов и проектные правила. Изменение контекста даёт HTTP 409 и предложение запустить генерацию заново. При совпадении используются сохранённые записи направлений, без повторной генерации или нового выбора из кеша.

Ссылка DS разрешается один раз в пределах вызова и передаётся в генерацию как снимок. Receipt хранится в штатном ограниченном SQLite-кеше с его TTL/LRU. Старые клиенты без receipt поддерживаются, но не получают защиты prepare/finalize от изменения контекста.

Ответ содержит sidecar `designPolicy`: version/hash, выбранный сценарий, requested/effective mode и неизвестные проверки. Эти поля не записываются как неподдерживаемые поля внутри Design IR.

## 4. Design System имеет приоритет

- `strict`: только точные мастера и разрешённые slots. Никакого автоматического перехода на extend. Нехватка мастера или контекста — явный отказ; закреплённый большой мастер можно материализовать и переписать только текстовые slots.
- `extend`: зарегистрированные мастера сохраняются; недостающие элементы создаются в foundations системы.
- `style-only`: основы системы обязательны, композиция свободнее.
- `tokens-only`: фиксируются переданные основы, без притворного подтверждения component provenance.
- `freeform`: coherent foundations и композиция выбираются по задаче и стилю.

`allowStrictFallback=true` оставлен как явная совместимость API для прежних клиентов; нода всегда передаёт false. Если он включён, фактический extend отражается в ответе и журнале.

Generic autofix и перепривязка inline-стилей не меняют strict-результат и макеты с exact refs. Исчезла обязательная сетка 8 px: шаг выбранной DS может быть другим. Component lint не требует H1 и размеров страницы. DS foundations имеют приоритет над конкурирующим входом токенов.

При материализации исправлен ранее невалидный служебный output: `sourceMeta.kind=component-instance`, bounded meta `strictRecoveryReason` и `contentRewrite` описаны в IR schema и сохранении metadata. Контент после замены проверяется схемой и DS; при ошибке возвращается исходный мастер с сообщением.

## 5. Quality Pass

Нода передаёт `designSystem`, `surface` и `visualReview=true`. Серверный путь получает изображения через vision API; desktop-путь возвращает text/image_url сообщения существующему адаптеру GPT/Claude. Рендеры — desktop 1440 и mobile 390, с настоящим переключением viewport. Остальные ширины не считаются проверенными. Изображения desktop-пути кешируются по IR, policy и версии renderer/engine.

Repair принимается только после повторной оценки. Изменение tokens, hashes/ref/формы мастеров, появление новых lint-дефектов или замечаний, падение оценки и отсутствие успешного rejudge приводят к точному откату исходного IR. Финальный pass требует порога (по умолчанию 80), verdict=pass, отсутствия critical/major, блокирующего lint и DS ошибок.

Статусы: `preview-ready` после визуального прохода; `needs-work` при дефекте; `unverified` при оценке только IR. Keyboard, screen-reader и performance остаются `unknown`, поскольку пиксели не проверяют эти свойства. В интерфейсе непроверенный результат называется предпросмотром с незавершённой проверкой.

## 7. Границы и дальнейшая калибровка

Полный сравнительный набор из 05 с живыми GPT/Claude и слепой человеческой оценкой ещё не проведён. Числа 25/20/20/15/10/10 — политика продукта, не результат такого эксперимента. Нативные keyboard/focus/screen-reader/performance gates, анализ всех состояний потока, автоматическое подключение Mobbin и полноценные runtime-компоненты сторонних AI kits не реализованы этим изменением. Модель получает требования к ним в пределах возможностей IR.

Автоматическое определение surface — объяснимая эвристика, а не семантический классификатор; при неоднозначном брифе используйте явный тип. Старые DesignBrief и presets сохраняются ради совместимости; новые сценарии не принуждаются к их маркетинговой структуре.
