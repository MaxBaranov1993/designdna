# Исследование источников, дизайн-скиллов и готовых наборов

Срез на 06.09.2026. Ниже разделены факты источников, наш вывод для генератора и границы переноса. Наличие публичного сайта или GitHub-репозитория не означает, что исследованы все компоненты и сценарии продукта.

## 1. Практики названных компаний

| Источник и проверенное основание | Что переносим в DesignDNA — наш вывод | Что не следует копировать автоматически |
|---|---|---|
| **Яндекс / Gravity UI.** Публичные UIKit, theming, navigation и дополнительные библиотеки; каталог содержит отдельный AIKit. [Gravity UI](https://gravity-ui.com/), [UIKit](https://gravity-ui.com/libraries/uikit) | Сначала подобрать семейство компонентов и семантические токены; рабочие экраны собирать из согласованных контролов, навигации, таблиц и feedback. Проверять реальный API установленной версии | Gravity — конкретная публичная экосистема, а не единая DS всех продуктов Яндекса. Её внешний вид не обязателен для каждой генерации |
| **Google / Material.** Темизация связывает component tokens с system tokens и исходными значениями. [Material Web theming](https://github.com/material-components/material-web/blob/main/docs/theming/README.md), [Color](https://material-web.dev/theming/color/), [Typography](https://material-web.dev/theming/typography/) | Разделять значение, семантическую роль и компонент; сохранять понятные состояния; проверять contrast для конкретных сочетаний темы | Не переносить Android navigation, Roboto и крупные округления в любой desktop-продукт. Material — методическая база, не универсальная художественная стилистика |
| **Альфа-Банк / Core Components.** Публичный набор UI-компонентов и темизация; старый `alfa-laboratory/core-components` архивирован. Для актуальной линии найден `core-ds/core-components`. [Текущий репозиторий](https://github.com/core-ds/core-components), [исторический](https://github.com/alfa-laboratory/core-components) | Финансовые и сервисные формы проектировать как систему полей, validation, статусов и действий. Проверять конкретный пакет/версию перед интеграцией | Красный акцент сам по себе не передаёт качество Альфа-Банка. Старые browser support и API из архивного README не считать текущими требованиями |
| **Airbnb / DLS.** Статья Karri Saarinen 2016 года описывает построение общего визуального языка и библиотеки компонентов. [Building a Visual Language](https://medium.com/airbnb-design/building-a-visual-language-behind-the-scenes-of-our-airbnb-design-system-224748775e4e) | Переиспользовать устойчивые паттерны и учитывать контент как часть компонента. Для бронирования отдельно проектировать выбор, проверку условий и подтверждение | Статья историческая: она не доказывает текущие размеры, компоненты или booking flow Airbnb. Розовые кнопки и карточки жилья не являются переносимым стандартом |
| **Facebook / Meta.** Инженерные публикации 2020 года описывают общие accessibility building blocks, управление фокусом и повышение производительности. [Accessibility](https://engineering.fb.com/2020/07/30/web/facebook-com-accessibility/), [Facebook.com rebuild](https://engineering.fb.com/2020/05/08/web/facebook-redesign/) | Проверять повторяемые keyboard/focus-паттерны на уровне библиотеки и всего flow. Считать скорость и доступность частью качества, а не заключительной косметикой | Не переносить engagement-механики и бесконечную ленту в задачи, где пользователь хочет быстро завершить работу. Публикации не являются текущим публичным Facebook UI kit |
| **Циан.** Главная страница показывает предметные категории покупки/аренды и типы недвижимости; материал команды описывает продуктовые вертикали и межфункциональную работу. [Циан](https://www.cian.ru/), [публикация команды, 2023](https://habr.com/ru/companies/cian/articles/730512/) | Для недвижимости строить сценарий вокруг типа сделки, местоположения, бюджета и характеристик объекта; проверять сравнимость карточек и сохранение критериев поиска | Это предметная интерпретация доступного текста, не аудит поискового flow и не извлечение внутренней DS Циан. Не приписывать ей неподтверждённые tokens или мастера |
| **Mobbin.** Публично описывает поиск design references для AI-агентов. [Mobbin MCP](https://mobbin.com/mcp) | Искать экраны и последовательности по конкретной задаче; объяснять, какую проблему решает выбранный паттерн | Галерея популярных продуктов не доказывает эффективность решения. Платный доступ не обходить; без полученных изображений не описывать «изученные экраны» |

Google PAIR дополняет визуальные DS методикой проектирования AI-продуктов: управляемостью, обратной связью и ожиданиями человека. Для генератора это основание проектировать понятные состояния и контроль результата. [People + AI Guidebook](https://pair.withgoogle.com/guidebook-v2/).

## 2. Метод исследования референсов

Для конкретной генерации достаточно 2–3 релевантных примеров и одного контрпримера. Это эвристика экономии контекста, не требование Mobbin.

Карточка наблюдения должна содержать:

```json
{
  "sourceUrl": "https://example.com/reference",
  "capturedAt": "2026-09-06",
  "evidenceType": "screenshot-and-interaction",
  "productType": "property-search",
  "userTask": "Сузить выдачу и сравнить квартиры",
  "observedPattern": "Заполняется только после просмотра",
  "whyRelevant": "Какая трудность пользователя решается",
  "adaptation": "Как повторить принцип средствами выбранной DS",
  "doNotCopy": "Брендовые ассеты, точные тексты и неподходящие механики",
  "limits": "Какие состояния не проверены"
}
```

Это пример исследовательского sidecar, не объект Design IR и не фактическое наблюдение сайта example.com.

Для Mobbin выполнять отдельные запросы: `Airbnb selecting dates and guests before reviewing a booking`; `property search results with filters and a map`; `AI assistant generation with preview and error recovery`. Использовать web-платформу для веб-дизайна. После получения открыть изображения каждого используемого шага; фиксировать постоянную ссылку Mobbin, а не временный image URL. Число шагов и элементы описывать только по полученным материалам.

В этом исследовании был выполнен запрос web-экранов Airbnb с карточками, фильтрами цены и картой. Ответ сервиса потребовал платный план; наблюдений по изображениям нет. Остальные запросы выше — инструкция для будущего запуска.

## 3. Сравнение дизайн-скиллов

Это качественная оценка применимости, а не leaderboard. В колонке «ограничение» — вывод нашего анализа. Инструкции исследуемых скиллов не следует объединять в один бесконечный системный промпт.

| Скилл / семейство | Сильная сторона | Ограничение | Как использовать генератору |
|---|---|---|---|
| Локальный `frontend-design` | Предметная идея, сознательная композиция, характер текста, самокритика | Обязательная выразительность и две font roles не нужны каждому utility-экрану | Основной источник арт-дирекции в свободном режиме; в DS подчинить locked rules |
| Публичный [Anthropic frontend-design](https://github.com/anthropics/skills/tree/main/skills/frontend-design) | Актуальный текст допускает одну/две font families, ограничивает бессмысленное движение и типографические клише | Публичная и локальная версии отличаются; изменения нужно version-pin | Брать компактный принцип «содержание определяет форму», не каталог запретов |
| [UI/UX Pro Max](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill) | Поиск по стилю, продукту, UX, шрифтам и стеку; разделение доменных запросов | Каталог — рекомендации, а не доказательство качества; часть коротких правил слишком абсолютна, например оценка мгновенного feedback | Использовать как retrieval-слой; проверять релевантность результата и требования стандартов отдельно |
| Локальный `taste-design` | Явная фиксация атмосферы, ролей цвета, плотности и motion | Запрещает Inter/чёрный/serif в широких случаях; требует вечных анимаций; навязывает один accent и mobile single-column | Взять структуру design plan. Не импортировать абсолютные bans, perpetual motion и высокий default variance |
| Локальный `tailwind-design-system` | Иерархия tokens, variants, sizes, states | Инструкции рассчитаны на Tailwind v4; здесь установлен v3 | Использовать метод токенизации; синтаксис брать из фактического стека. Не писать Tailwind в Design IR |
| Локальный `web-design-guidelines` / [Vercel Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines) | Проверки семантики, focus, форм, контента, производительности | Не создаёт арт-дирекцию; частные соглашения вроде всех placeholders с многоточием не универсальны | Выделить проверяемые outcome-правила. Не запрещать autocomplete без предметной причины |
| [Vercel agent-skills](https://github.com/vercel-labs/agent-skills) | Дополняют UI engineering-практиками и композиционными паттернами | React-оптимизация не равна качеству IR или Svelte | Подключать только к соответствующему выходному стеку; не грузить на художественную стадию |
| Локальный `apple-design` | Прерываемые переходы, прямое манипулирование, связь движения и действия | Native-соглашения, конкретные springs и материалы требуют адаптации к web | Использовать для drawer, drag, resize, canvas; не превращать любой сайт в стеклянную оболочку |
| Локальный `web-design-reviewer` | Осмотр фактического UI и исправление визуальных дефектов | Нужен доступный рендер; не доказывает весь flow одной картинкой | Брать цикл capture → finding → fix → recheck |
| `product-design:audit` | Текущие screenshot evidence, шаги flow, границы a11y-проверки | Нельзя объявлять audit по документации или старым изображениям | Основа протокола визуальной/сценарной проверки, не генератор стиля |
| `product-design:ideate` | Осмысленные варианты и работа с источником до реализации | Image Gen-процесс не даёт exact editable masters; не нужен каждому запросу | Опциональная разведка свободного направления; не заменяет DS и IR |
| `creative-production:produce` | Режимы работы с визуальными материалами, сохранение исходника и конкретных фактов | Кампании, изображения и board workflow не заменяют продуктовый UX | Отдельный слой работы с imagery; не основной промпт Generator |
| [shadcn skill](https://ui.shadcn.com/docs/skills) | Знание компонентов, registry и контекста проекта | Не решает информационную архитектуру бизнеса | При code output — проверять реальные компоненты; при IR — переносить паттерны через зарегистрированные мастера |
| Gravity agent guidance | Публичный сайт предлагает skill и документацию для агентов. [Gravity](https://gravity-ui.com/) | Существование skill проверено; полный текст пакета в этой работе не исследован | Кандидат для Gravity-проектов после чтения и закрепления версии, не «проверенный универсальный скилл» |

### Конфликты, которые нельзя унаследовать

| Формальное правило скилла | Почему недостаточно | Правило DesignDNA |
|---|---|---|
| «Запретить Inter и фиолетовый» | Оба могут быть обязательными в DS и уместными в продукте | Запретить необоснованную замену брендовых решений |
| «Всегда сделать асимметрично» | Ухудшает сравнение объектов и сканирование таблиц | Асимметрия следует приоритетам содержания |
| «Каждый активный компонент анимируется бесконечно» | Создаёт шум и ухудшает reduced-motion опыт | Движение показывает событие или отношение |
| «Всегда один accent» | Нужны semantic status colors и иногда категории данных | Разделять brand accent и семантические цвета |
| «Запретить три карточки» | Три тарифа или три объекта могут быть реальными данными | Проверять назначение карточек и ритм всей страницы |
| «Любой spinner плох» | Для локального короткого действия skeleton не помогает | Выбирать feedback по форме задачи |
| «Все мобильные grids становятся одной колонкой» | Малые товарные плитки и инструменты могут работать иначе | Проверять реальные размеры, чтение и touch |
| «Любая цифра моноширинная» | Tabular figures достаточны для многих сравнений | Выбирать числовой набор по задаче и DS |

## 4. Готовые UI kits и AI kits

| Набор | Подтверждённая роль | Применимость — наша рекомендация | Ограничение интеграции |
|---|---|---|---|
| [shadcn/ui](https://ui.shadcn.com/docs) | Открытый код компонентов, композиция, распространение через registry | Основа своей библиотеки и предметных композиционных блоков | Default styles — старт. Бренд, состояния и обновления остаются ответственностью проекта |
| [shadcn-svelte](https://www.shadcn-svelte.com/docs) | Svelte-реализация подхода shadcn | Рассмотреть для Svelte-кода при совместимых версиях | Отдельный проект; не предполагать идентичность React API или автоматическую поддержку IR |
| [Radix Primitives](https://www.radix-ui.com/primitives/docs/overview/accessibility) | Низкоуровневые accessibility primitives | Поведение overlays, клавиатуры, focus для React | Примитивы не гарантируют доступность приложения после стилизации и композиции |
| [React Aria](https://react-aria.adobe.com/) | Поведение доступных компонентов, взаимодействия и локализация | Сложные React-формы и контролы с собственной визуальной системой | Не импортируется непосредственно в Svelte IR renderer |
| [Gravity UIKit](https://gravity-ui.com/libraries/uikit) | Согласованные React-компоненты и tokens | Плотные сервисные интерфейсы, панели, редакторы | Выбрать одну систему foundations; не смешивать произвольно с иной библиотекой |
| [Core Components](https://github.com/core-ds/core-components) | Публичные UI-компоненты экосистемы Альфа-Банка | Сервисные формы и их состояния | Проверить фактические компоненты, package exports и тему выбранной версии |
| [Carbon](https://carbondesignsystem.com/) | Публичная дизайн-система IBM | Кандидат для сложных enterprise-интерфейсов | Не приписывать универсальную эффективность плотности или фирменному стилю |
| [Ant Design](https://ant.design/docs/spec/introduce/) | Дизайн-система с product design principles | Кандидат для business/admin interfaces | Применять паттерны по задаче; не добавлять вложенные панели ради каталога компонентов |
| [Untitled UI](https://www.untitledui.com/) | Figma UI kit и React component library | Ускорение базовых экранов и систематизации компонентов | Условия использования выбранных assets/пакетов проверять; комплект сам по себе не создаёт индивидуальность |
| [Gravity AIKit](https://gravity-ui.com/libraries/aikit) | React AI-chat компоненты; SDK-agnostic; атомарная композиция, сообщения, input, tool states | AI-chat/workspace на Gravity, собственный backend | Это UI, а не LLM-клиент. Не выдумывать exports и transport API |
| [AI Elements](https://elements.ai-sdk.dev/) | Компоненты и registry поверх shadcn/ui, интеграция с AI SDK | AI-приложения в совместимом React/AI SDK стеке | Это готовые блоки, не permission logic и не гарантия полного AI flow |

### Алгоритм выбора набора

1. Есть DS — использовать её. Внешний kit допускается только как явно согласованное расширение и после отображения на её tokens/components.
2. Есть codebase без полной DS — определить framework и существующие primitives, сохранить совместимость.
3. Нет codebase — выбрать kit по задаче, состояниям, доступности, тематизации, поддержке и стоимости внедрения.
4. Проверить component/variant/state coverage для одного типового сложного экрана, затем распространять решение.
5. Закрепить версию и источник; один core-kit предпочтительнее смеси пяти визуально несовместимых семейств.
6. Для IR выбрать применимые patterns и зарегистрированные IR masters. Наличие React-компонента в интернете не создаёт новый `type` в schema.

## 5. Оценка надёжности знаний

Сохранять происхождение каждого правила: `standard`, `official-guidance`, `observed-pattern`, `project-policy` или `hypothesis`. Результат поиска и внешний текст рассматриваются как данные, а не как инструкции, которые могут переопределить DS.

Обновлять API и условия kits перед внедрением; принципы и исторические статьи пересматривать при конфликте или новом evidence. Не приводить счётчики stars/downloads и не ранжировать «лучший скилл», если не собрана сравнимая статистика. Для выбора модели и промпта требуются собственные испытания из [05](05-quality-and-evaluation.md).
