# Приёмка, визуальная оценка и испытания GPT/Claude

Это предлагаемая политика DesignDNA. Порог `release-ready` ниже — проектная гипотеза, которую нужно откалибровать. Текущая rubric и gate не изменены этим документом.

## 1. Разделять четыре вида качества

1. **Корректность:** схема, поддерживаемые узлы, разрешимые ресурсы и refs.
2. **Верность DS:** точные мастера/варианты и допустимые изменения.
3. **Визуальное исполнение:** иерархия, ритм, типографика, предметность.
4. **Рабочий UX:** доступные действия, состояния, keyboard, responsive, сохранение данных.

Первые два часто проверяются программно; третий требует рендера; четвёртый — взаимодействия и ручной проверки применимых сценариев. Нельзя свести всё к одному числу vision judge.

## 2. Hard gates

| ID | Требование | Доказательство | Реакция |
|---|---|---|---|
| G01-schema | IR соответствует выбранной версии и renderer capability | JSON schema + semantic validation | Reject/repair |
| G02-ds-ref | DS ref разрешается; revision/contentHash закреплены | Результат resolver | Reject до генерации |
| G03-master | В strict refs/hash/вариант/форма и покрытие совпадают с registry | Deterministic DS validation + asset/slot checks | Strict fail; не маскировать extend |
| G04-scope | Нет самовольного изменения locked values, контента и чужих областей | Diff против input/master | Reject/repair |
| G05-geometry | Нет непреднамеренного clipping, перекрытия важных элементов, escape | Bounds/DOM + screenshot каждого viewport | Reject/repair |
| G06-task | Главное действие и критические шаги доступны и соответствуют брифу | Flow test или явно ограниченный prototype review | Needs work; при отсутствии проверки unknown |
| G07-content | Нет вымышленных доказательств, необозначенных demo и поддельных источников | Content provenance + review | Reject/исправить текст |
| G08-assets | Нет broken assets; placeholders имеют назначение и честный статус | Asset resolution + screenshot | Preview допускает описанный placeholder; готовый сайт требует финального решения |
| G09-a11y | Применимые contrast/keyboard/name/focus/reflow требования выполнены | Автопроверки + ручной flow review | При дефекте fail; без evidence unknown |
| G10-repair | Правка не нарушает DS и не добавляет дефекты | Повторные gates + сравнение before/after | Откат к предыдущему валидному результату |

Наличие `critical` или `major` дефекта не компенсируется баллами за цвет. `unknown` по обязательной проверке не превращается в `pass`.

Для компонентного preview G06 относится к локальному действию/состояниям компонента. Рекламное обещание, navbar и финальный CTA не требуются.

## 3. Матрица рендера и поведения

Минимальная проектная матрица:

- Desktop 1440 px, tablet 768 px, mobile 390 и/или 360 px согласно целевым устройствам.
- Reflow при 320 CSS px; текстовое увеличение 200%; применимые исключения документируются. Не объявлять любую двумерную прокрутку нарушением.
- Default, loading, empty, error, success; disabled/selected/expanded — где есть такие состояния.
- Короткий, обычный и длинный контент: длинный русский заголовок, большая цена, неизвестное изображение, 0/1/много объектов.
- Keyboard: Tab/Shift+Tab, Enter/Space где уместно, Escape для соответствующих overlays, видимый/неперекрытый focus и возврат к инициатору.
- Reduced motion; обе темы — только если они входят в продуктовый scope или DS.
- Primary flow, error recovery, возврат/undo — на реально реализованной поверхности.

Сохранять viewport, state, размеры, timestamp, IR hash, DS ref и renderer/font identity вместе с evidence. Сначала дождаться шрифтов/изображений и проверить, что screenshot не пустой и не экран загрузки.

Для недоступного интерактивного renderer можно принять `preview-ready`, но не `release-ready` и не полное WCAG compliance. Canvas-макет не доказывает semantic HTML будущего сайта.

## 4. Визуальная rubric: 100 баллов

| Категория | Вес | Что оценивается |
|---|---:|---|
| Ясность задачи и информации | 25 | Порядок чтения, главное действие, видимость необходимых условий, отсутствие лишнего |
| Соответствие identity и согласованность | 20 | DS или созданные foundations, shared patterns, предметный характер |
| Типографика и layout | 20 | Роли, переносы, выравнивание, шкала отступов, плотность, адаптивная композиция |
| Состояния и понятность взаимодействия | 15 | Читаемость выбранного/ошибочного/загружаемого состояния и доступных действий по представленному evidence |
| Контент и изображения | 10 | Конкретность, релевантность, происхождение, роль медиа |
| Обоснованность визуальных решений | 10 | Нет декоративного заполнения, шаблонных блоков без задачи, непоследовательных приёмов |
| **Всего** | **100** | |

В strict категория identity оценивает точность и согласованность, а не оригинальность относительно мастера. В свободном режиме — связь выбранной системы с предметом. За «слишком обычную кнопку» баллы не снимать.

Предлагаемая шкала после hard gates:

- `<80`: нужна доработка.
- `80–89`: хороший рабочий preview, локальная полировка по замечаниям.
- `≥90`: кандидат на высокий визуальный уровень; `release-ready` только при подтверждённых обязательных UX/a11y-проверках.

Число — помощь ревьюеру, не доказательство «первоклассности». Текущий код использует другую rubric с порогом 80; миграция требует отдельной калибровки на эталонных работах.

## 5. Контракт замечания

Пример предлагаемого QA sidecar, **не фактический отчёт и не объект текущей API-схемы**:

```json
{
  "policyVersion": "generator-design/1.0",
  "requestedMode": "strict",
  "effectiveMode": "strict",
  "status": "needs-work",
  "visualScore": 76,
  "checks": {
    "schema": "pass",
    "designSystem": "pass",
    "geometry": "fail",
    "keyboard": "unknown"
  },
  "issues": [
    {
      "ruleId": "G05-geometry",
      "severity": "critical",
      "sourceKey": "example-card-title",
      "path": "tree.1.children.0",
      "viewport": 360,
      "state": "long-title",
      "evidence": "screenshots/mobile-long-title.png",
      "observed": "Название закрывает строку цены",
      "fix": "Выбрать зарегистрированный mobile-вариант; если его нет, зарегистрировать DS gap",
      "scope": "variant-selection"
    }
  ]
}
```

Для evidence использовать существующие файлы; пример выше не утверждает наличие изображения. Не писать «улучшить визуал». Замечание должно объяснять, что наблюдается и какая разрешённая правка устранит проблему.

## 6. Доработка и остановка цикла

1. Проверить severity и ownership: instance, composition, master или missing capability.
2. Взять минимальный связанный набор исправлений.
3. Применить правку в копии IR; исходник сохранить.
4. Повторить schema/DS/bounds, затем рендер и применимые сценарии.
5. Сравнить дефекты по ruleId + sourceKey + viewport + state, чтобы изменение индексов дерева не выглядело как «исправление».
6. Принять только если targeted issues устранены, нет новых дефектов и не ухудшена ранее пройденная проверка. Более строгая локальная политика имеет приоритет.
7. Политика первоначального rollout: до двух автоматических repair-попыток, затем честный `needs-work` со списком нерешённых проблем. Это лимит продукта, не ограничение возможностей модели.

Если проблема принадлежит exact master, Generator не исправляет её молча внутри экземпляра. Нужна отдельная проверяемая операция изменения DS.

## 7. Испытания промптов и провайдеров

Сравнивать текущие промпты и предлагаемые на одном immutable наборе задач. Не сравнивать лучший результат Claude с первым неудачным GPT. Не удалять failed runs из статистики.

Предлагаемый первый набор: **12 задач × 2 состояния DS × 2 провайдера × 3 повторения = 144 запуска** на одну версию политики. Baseline и candidate вместе — 288 запусков. Режимы DS: strict с подготовленной подходящей системой и freeform; gaps/extend/style-only проверять дополнительными кейсами ниже. Это план, запуски в этой работе не выполнялись.

| № | Бриф | Что отличает хороший результат |
|---:|---|---|
| 1 | Поиск квартиры для аренды | Фасеты, сравнимые свойства, цена/период, сохранение критериев |
| 2 | Карточка услуги и запись | Услуга, исполнитель, доступность, условия, подтверждение |
| 3 | Каталог предметов интерьера | Материал, размер, цена, работающие image slots |
| 4 | Рабочая таблица заказов | Статус, сортировка, действие; высокая информационная плотность |
| 5 | Форма реквизитов | Labels, validation, длинные значения, saving и error |
| 6 | AI workspace с preview | Контекст, stop/retry, preview/apply/undo |
| 7 | Статья с длинным русским заголовком | Читаемая строка, media, навигация без marketing shell |
| 8 | Лендинг мастерской без фото | Предметность, honest placeholders, без вымышленных отзывов |
| 9 | Учебный сервис для взрослых | Дружелюбность без infantilization, ясный следующий шаг |
| 10 | Инженерный продукт | Содержательная спецификация без fake telemetry |
| 11 | Настройки уведомлений | Группы, выбор, сохранение; отсутствие hero |
| 12 | Canvas-редактор | Рабочая область, selection, свойства, история и клавиатурная альтернатива |

Дополнительные adversarial-кейсы:

- DS на Inter, фиолетовом и симметричных карточках: anti-slop не меняет бренд.
- Обязательный вариант отсутствует: явный gap, без ложного strict success.
- Мастер слишком велик для бюджета: нет тихого усечения и подмены.
- Reference требует другого бренда: фиксируется конфликт/ограничение.
- В DS есть только desktop-вариант: mobile не объявляется проверенным.
- Нет evidence keyboard/performance: статус unknown.
- Только один тариф: генератор не придумывает ещё два.
- Запрос на один компонент: нет страницы из 6–8 секций.
- Изменение locked master под предлогом repair: отказ/откат.
- Provider отказал, ответ оборван, JSON невалиден: нет красивого, но пустого результата.
- Повторный экран проекта: сохранена общая навигация и vocabulary.
- Prompt injection внутри reference: не меняет policy и DS.

## 8. Метрики и принятие кандидата

Собирать по provider/model, surface и mode:

- First-pass schema rate и hard-gate pass rate; для strict отдельно exact-master pass rate.
- Число refs/variant/asset ошибок, ложных `ready`, вымышленных фактов.
- Repair rate, успешность repair, число новых дефектов после repair.
- Медиана и разброс визуальных оценок; слепое попарное предпочтение ревьюеров.
- Доля успешно завершённых сценариев, если есть интерактивный output.
- Стоимость и время: p50/p95, число вызовов, входные/выходные токены, включая ошибки.
- В свободном режиме — предметное разнообразие структуры между разными брифами; при общей DS — согласованность экранов.

Для честного сравнения закрепить fixtures, модели, budgets, доступные tools/assets и renderer. Если меняется judge, повторно оценить и baseline. По возможности скрыть имя провайдера и порядок кандидатов; разногласия ревьюеров сохранять, а не усреднять до уверенного verdict.

Кандидат допускается к ограниченному rollout, когда обязательные контрактные кейсы проходят, нет ложных ready и регрессий strict, а визуальные/сценарные результаты лучше baseline при приемлемых затратах. Не делать вывод о превосходстве модели по одному красивому скриншоту. При 144 запусках редкие дефекты всё ещё могут быть не замечены.

## 9. Финальный checklist для одного результата

- [ ] Пользователь узнаёт свою задачу и следующий шаг.
- [ ] Фактический режим совпадает с заявленным; DS refs/variants проверены.
- [ ] Не добавлены неподтверждённые факты и ненужные sections.
- [ ] Визуальные роли последовательны; длинный контент не ломает layout.
- [ ] Рендеры целевых viewport просмотрены, а не просто сохранены.
- [ ] Состояния проверены в пределах возможностей продукта.
- [ ] Keyboard/a11y/performance не объявлены пройденными без соответствующего evidence.
- [ ] После repair повторены затронутые проверки, новые дефекты не появились.
- [ ] Placeholders и ограничения честно отражены в итоговом статусе.
